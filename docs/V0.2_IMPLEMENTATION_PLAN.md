### 1.2 Critical gaps (why v0.1 is not sellable)

**Money path is broken end-to-end:**
1. **Payments are 100% mock.** `RazorpayMockProvider` is hardcoded; `create_order` fabricates IDs locally; webhook verifies signature then discards the event; refunds are local status flips; payment amount never validated against order total. No money can move.
2. **No inventory exists.** `modules/inventory/*` are empty files; no stock columns, no reservation, no decrement, no row locks (`with_for_update`: 0 hits). Festival launch = guaranteed overselling.
3. **Checkout fabricates orders for guests** — shows a fake confirmation with locally generated ID `ELK{timestamp}` and destroys the cart.
4. **Coupons never reach orders.** `discount_total` is always 0; frontend validates against a hardcoded coupon map — every festival promo code shown to customers would be fake.
5. **Checkout ignores the server cart**; order creation never references it.
6. **Customers cannot place real orders at all**: `OrderService._get_current_business_id()` 401s because storefront customers have no business membership, so `app.business_id` is never set.
7. **Tax/shipping hardcoded 0**; no shipping rules.

**Storefront:**
8. Catalog mapping written against a nonexistent API shape (`base_price`/`compare_at_price`/`images[]` vs actual `price`/`media[]`) → NaN prices, broken images the moment the static fallback is dropped; API `limit/offset` params never sent.
9. No Compare feature (buttons dead). Wishlist add-buttons dead (page reads API JSON but nothing ever adds). No real search endpoint usage (client-side substring filter). No specs/related-products data. Fake reviews tab.
10. SEO: no sitemap.ts, no robots.ts, no per-product metadata, no JSON-LD, zero `next/image` usage.
11. Fake UX: hardcoded COUPONS map, newsletter lie, pincode-serviceability fake, contact form fake, "Ask Emi" fake.

**Admin:**
12. Product form has 4 fields; no images (R2 media router exists but unmounted and broken), no categories/brand/MRP/stock/publish.
13. Inventory, Analytics, Users pages are hardcoded theater; no order-status UI; `/customers/[id]` fetches a relative URL (broken); no coupons UI; no role gating (any customer can log in and browse).

**Security:**
14. No rate limiting anywhere. No password reset. Tokens in JS-readable cookies without `Secure` flag. Carts router has IDOR (no ownership checks; any user can read/mutate any cart). `GET /orders/{id}` has no ownership check for customers. `/api/v1/businesses` CRUD is unauthenticated (127 junk businesses in prod DB prove it's been used). `/api/v1/settings` trusts a spoofable `x-business-id` header. `payment_events` has no RLS. `users` SELECT policy is `USING(true)`. A Supabase password is hardcoded in `apply_rls.py` (leaked in git history). `RequestIdMiddleware` written but never mounted.

**Infrastructure:**
15. **Storefront has no Dockerfile, no compose service, no nginx vhost, no cert** — `elektrix.in` serves a stale Vercel build of the old static catalog; the VPS cannot serve it.
16. **admin.elektrix.in has no DNS record at all**; the admin container has no nginx proxy_pass and ships with `NEXT_PUBLIC_API_URL=http://localhost:8000` baked in.
17. CI runs zero tests; deploy workflow not gated on CI; deploy rollback doesn't revert migrations; certbot renewal config is corrupt (0-byte conf, dangling lineage); Makefile `make test`/`db-migrate` broken.

**Notifications:**
18. Email provider is a logger stub; outbox helper has zero callers; ARQ handler is a sleep-stub. No order-confirmation email will ever send.

## 2. Architecture Decisions for v0.2

### D1 — Single-store operation over multi-tenant schema (seller-ready)
Keep the `business_id` multi-tenant schema untouched (future v1.1 sellers). Introduce `STORE_BUSINESS_ID` (env) = the canonical ELEKTRIX store. All storefront customer flows default their tenant context to the store business (customers get no membership). Admin flows use the store business too. RLS policies gain user-ownership clauses where customers self-scope (orders, carts, addresses, wishlists, notifications) plus an `app.role` GUC for staff/platform_admin bypass. This preserves the seller-marketplace path without building seller features.

### D2 — Inventory model
New `inventory` table: one row per product (`product_id` UNIQUE, `on_hand`, `reserved`, CHECK `on_hand >= 0 AND reserved >= 0`), available = on_hand − reserved. `inventory_movements` audit (delta_on_hand, delta_reserved, reason enum, reference, actor). All mutations via atomic SQL (`UPDATE ... WHERE on_hand - reserved >= n RETURNING`) or `FOR UPDATE` row locks. Reservation at order creation; commit on payment success/COD confirm; release on cancel/expiry/payment-failure. Variants share the product's stock pool in v0.2 (documented).

### D3 — Payment provider abstraction (provider-agnostic)
`PaymentProvider` base (exists) with three implementations: `RazorpayProvider` (real REST via httpx: Orders/Fayments/Refunds), `MockProvider` (tests/local), future providers selectable via `PAYMENT_PROVIDER` env. Amount always validated server-side against order total. Webhook processes `payment.captured|failed|refund.processed` idempotently and is the source of truth; client-side verify remains as UX fast-path with the same idempotent transition logic. All events appended to `payment_events`. Live Razorpay keys are already configured.

### D4 — Checkout as one transactional service
`POST /api/v1/orders/checkout` (auth required — guest checkout removed): resolves cart (or explicit items) → locks inventory rows → validates stock + coupon (atomic usage increment) → computes subtotal/discount/shipping/COD-fee server-side (GST-inclusive pricing: `tax_total` stays 0 by design, documented) → creates order `PENDING` (online) or `CONFIRMED` (COD, stock committed) + payment record + address snapshot + order number `ELK-YYMMDD-XXXXX` → reserves stock → records outbox events → clears cart. Idempotency via key with IntegrityError-safe dedup.

### D5 — Addresses & wishlists become first-class tables
`addresses` (ownership-scoped, default flag, validated pydantic: name/phone/line1/line2/city/state/pincode/country, phone+pincode regex). `wishlist_items` (user_id+product_id UNIQUE). Orders snapshot the address at purchase (already JSON snapshot — now sourced from the addresses table). Legacy `users.addresses/wishlist` JSON kept read-only for backward compat.

### D6 — Notifications via outbox → ARQ → providers
`outbox_events` (exists) written inside the checkout/payment/status-transition transactions. ARQ worker dispatches to `NotificationService` → providers: Resend HTTP API (email, configured) + in-app (`notifications` table). Templates: welcome, order confirmation, payment success/failure, shipped, delivered, cancelled, refund, password reset. Retries with backoff, dead-letter marking after N attempts, idempotent (event_id dedup). SMS/WhatsApp providers stub the same interface for later.

### D7 — Search: PostgreSQL only
`pg_trgm` + `tsvector` on products (name/sku/brand/description) with GIN indexes; `/api/v1/products/search?q=` (public) + storefront debounced header search. No Elasticsearch. The vector/Gemini module stays unmounted for v0.2.

### D8 — Festival offers engine (scheduled product offers)
Products gain `mrp` (list price), `sale_price`, `offer_starts_at`, `offer_ends_at`, `status` (DRAFT/ACTIVE/ARCHIVED), `featured`, `brand`, `slug`, `category_id`, `specs` JSONB, `tags`. Effective price = `sale_price` when within the active offer window, else `price`. Backend computes it everywhere (list, detail, cart, checkout) — frontend never computes prices. Plus admin-managed storefront banner content (`store_settings` key/value on `business_settings`).

### D9 — Auth: keep Bearer-in-localStorage for v0.2, harden around it
Moving to httpOnly cookies is a full auth rework (CSRF, both frontends, rotation flows) with high regression risk days before the festival. v0.2 keeps the existing Bearer pattern but: adds `Secure` cookie flags + short-lived tokens (already 15 min), nginx security headers + CSP, rate limiting on auth endpoints, password reset flow, and IDOR/ownership enforcement. Cookie migration documented as v0.3 top security item.

### D10 — Storefront moves to this VPS
Root storefront app gets a standalone Dockerfile (Next standalone), compose service `storefront` (2 replicas), nginx server blocks for `elektrix.in` + `www.elektrix.in` + `admin.elektrix.in` with correct `NEXT_PUBLIC_API_URL=https://api.elektrix.in` build args. Certs via certbot webroot for the two new domains (requires DNS — see Risks). Vercel keeps serving until the DNS A record is repointed (one Cloudflare change, documented for the owner — cannot be done from this VPS: no Cloudflare credentials).

### D11 — Data strategy: scope, don't delete
The 127 junk businesses are not deleted (no destructive prod action). The storefront and admin operate exclusively on `STORE_BUSINESS_ID`; junk tenants are invisible. A seed script creates the canonical ELEKTRIX business, categories, products (with real imagery via R2/`media.elektrix.in`), festival coupons, and ensures an admin owner account exists. Full DB backup taken before any migration.

## 3. Database Changes (single Alembic revision `v02_commerce`)

**New tables:** `inventory`, `inventory_movements`, `addresses`, `wishlist_items`, `notifications`, `newsletter_subscribers`.
**New columns:** products (`mrp`, `sale_price`, `offer_starts_at`, `offer_ends_at`, `status`, `featured`, `brand`, `slug`, `category_id` FK, `specs` JSONB, `tags`); orders (`order_number` UNIQUE, `coupon_code`, `payment_method`, `tracking_number`, `tracking_url`, `shipped_at`, `delivered_at`); payments (amount Float→Integer fix via ALTER).
**Enums:** `productstatus` (DRAFT/ACTIVE/ARCHIVED), `inventoryreason` (RESTOCK/SALE/RESERVE/RELEASE/ADJUST/COUNT/RETURN/DAMAGE).
**Indexes:** products (slug, status, category_id, business_id+status, trigram GIN on name/sku/brand, tsvector GIN), inventory (product_id UNIQUE), addresses (user_id), wishlist_items (user_id, UNIQUE user+product), notifications (user_id+created_at, user_id+read_at), orders (user_id, order_number), inventory_movements (product_id+created_at).
**Checks:** inventory on_hand≥0, reserved≥0; addresses pincode 6 digits (app-level + length check).
**RLS updates:** enable+policy all new tables (ownership-scoped: user_id = app.user_id, staff bypass via app.role GUC); tighten `users` SELECT to self-or-staff; add policy for `payment_events` (tenant + staff); set `app.role` GUC in `set_db_context`.

## 4. API Changes (all under /api/v1)

- `POST /orders/checkout` (new; replaces client-composed order creation for storefront), order number in responses; `GET /orders` customer-scoped (user_id forced for non-staff); `GET /orders/{id}` ownership-checked.
- `GET /orders/track/{order_number}` public-with-email? No — auth + ownership (existing tracking page pattern kept).
- `GET /products/search?q=`, `GET /products/?category=&status=&featured=&q=&min_price=&max_price=&sort=` (public, store-scoped, effective-price computing, pagination).
- `GET /categories` public tree for the store.
- Addresses CRUD + set-default; Wishlist add/remove/list; Notifications list/unread-count/mark-read.
- Coupons: public `POST /coupons/validate` (rate-limited, customer-auth) for checkout preview; redemption only inside checkout transaction.
- Payments: real provider init/verify; webhook processes events; refunds (staff) via provider API.
- Admin (role-gated `owner|staff|platform_admin`, server-side enforced): `GET /admin/dashboard` (today's orders/revenue, pending, low-stock, out-of-stock, pending payments, recent orders, top products, active offers), inventory list/adjust, product publish/feature/offer, banners, customers, users list, coupons CRUD (exists), order status/tracking updates.
- Security: mounted RequestId middleware, Redis rate limiter (login/register/reset 10/min/IP; coupon validate 20/min; search 60/min; checkout 10/min/user; admin 120/min), businesses router auth, settings tenant fix, carts ownership, password reset endpoints (`/auth/forgot-password`, `/auth/reset-password`).
- Health: `/health/diagnostics` reports truthful module status (no hardcoded green).

**Admin (apps/web):** real dashboard from `/admin/dashboard`; product manager (all fields, R2 presigned image upload with ordering, variants, publish/feature/offer scheduling); inventory manager (stock, adjust with reason, low-stock view); order manager (filters, detail, status transitions, tracking, refunds); customers (fixed); coupons manager; settings incl. ## 6. Testing Strategy

- **Backend (pytest, async, against real Postgres via docker compose pgvector + Redis):** auth (register/login/refresh/reset/roles), products (catalog filters/search/effective price), inventory (reserve/release/commit; **concurrency: N parallel buyers vs 1 unit of stock — exactly one succeeds; stock never negative**), cart (ownership, merge), coupons (atomic limits under concurrency), checkout (totals, idempotency, COD vs online, stock reservation), payments (mock provider full lifecycle + webhook idempotency + amount-tamper rejection), notifications (outbox→worker), admin authorization (customer hitting admin endpoints = 403, IDOR checks).
- **CI:** pytest runs in `ci.yml` (was missing), storefront+admin typecheck+build (exists), compose config validation (exists); deploy workflow gated on CI success.
- **E2E (post-deploy, on VPS):** scripted API smoke (register→login→browse→cart→coupon→checkout COD + online(mock-sandbox)→order→notification→tracking; admin: login→product→stock→order status) + browser-automation pass over the critical mobile journeys.

## 7. Deployment Strategy & Rollback

1. `pg_dump` full backup before migration (kept on VPS + documented restore).
2. Local commits on `main` in logical units; deploy via `infra/scripts/deploy_vps.sh` (build → `alembic upgrade head` → `up -d` → health checks → rollback on failure) — the same script GitHub Actions runs.
3. Migration is additive-only (new tables/columns nullable-or-defaulted) → old containers keep working during rollout; rollback = `docker compose` previous tag + `alembic downgrade -1` procedure documented (additive tables make downgrade safe).
4. Nginx gains server blocks; certs for new domains via `setup_ssl.sh` (extended) once DNS exists.
5. Post-deploy: smoke suite + `/health/diagnostics` truthfulness check.

## 8. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| DNS for `admin.elektrix.in`/`elektrix.in` cannot be changed from this VPS (no Cloudflare credentials) | Everything is wired so a single Cloudflare A-record change completes launch; explicit handover instructions in release notes. Until then storefront stays on Vercel (stale) — API/admin ready behind DNS. |
| Live Razorpay keys active — a broken checkout charges real money | Mock provider default in non-prod ENV_NAME; live only when `PAYMENT_PROVIDER=razorpay` + `ENV_NAME=prod`; webhook secret verified; amount server-validated; ₹1-limited live test documented post-deploy. |
| Migrations against live Supabase | Additive-only, single revision, full backup first, `alembic upgrade` inside deploy script with rollback doc. |
| No git push access — CI/CD can't run from here | All commits local on `main` (clean history for later push); deployment executed via the same script CD uses; documented for owner to push & reconnect Actions. |
| Cart/wishlist data migration (users JSON → tables) | Lazy migration: on first wishlist/address API call, JSON contents are copied into tables (idempotent upsert). |
| Storefront regression on mobile | Browser-automation pass on mobile viewport for the 8 critical journeys before sign-off. |
